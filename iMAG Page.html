n8n on Google Cloud Run — Migration & Operations Guide

Our n8n workflow automation platform has moved off a local Docker container on a single Windows PC and onto Google Cloud Run, backed by a managed Postgres database. It now runs independently of any one machine, and the whole thing sits on free-tier infrastructure. This guide covers what was built, how to get in and work with your workflows, what changed from the old setup, and how to operate and troubleshoot it.

What This Is

Previously, n8n ran in a Docker container on a local PC, storing everything in a single SQLite file at D:\n8n_data. That meant automations only ran while that specific machine was on, and all 52 workflows plus their credentials lived in one 1.5 GB file on one disk.

n8n now runs as a container on Google Cloud Run, with all of its state (workflows, credentials, execution history) stored in a Supabase Postgres database. Cloud Run starts the container on demand and shuts it down when idle, so there is no server to maintain and no ongoing compute cost at typical usage levels.

Everything was migrated: 52 workflows and 26 credentials. Because the original encryption key was carried across, none of the credentials had to be re-entered — they decrypt exactly as before.

Who This Guide Is For

  • Whoever operates or edits the automations — the day-to-day work of opening the editor, changing workflows, and re-enabling triggers.
  • Whoever needs to maintain the deployment — redeploying the container, checking logs, rotating credentials, or diagnosing an outage.

It assumes comfort with Docker, the gcloud CLI, and n8n itself. It is not a beginner's introduction to n8n.

How to Access and Edit Workflows

  1. Open the editor at https://n8n-659687081407.australia-southeast1.run.app.
  2. First visit only: n8n will prompt you to create an owner account (email and password). User logins were deliberately not migrated, so this is a fresh account — it is unrelated to your old local login.
  3. Edit workflows exactly as you did locally: open a workflow, change nodes, hit Save. Changes write straight to the Supabase database.
  4. To bring a workflow back to life, open it, re-enable its trigger node (all triggers were disabled during migration — see below), then flip the Active toggle in the top right.

You do not need to redeploy anything to change a workflow. Editing workflows, credentials, and settings in the UI persists directly to the database. A redeploy is only needed when the container image, environment variables, or secrets change.

Important: All Triggers Were Disabled

This is the single biggest behavioural difference from the old setup, and it was a deliberate cost decision.

All 13 previously-active workflows were driven purely by Schedule (cron) triggers — 29 of them in total, once you count the ones buried inside individual workflows. Cloud Run's free tier depends on the container scaling to zero when idle, and n8n's internal cron scheduler only fires while the container is actually running. Driving those schedules from the cloud instead would have required roughly 26 billable Cloud Scheduler jobs (about US$2.60/month).

Rather than incur that, all 29 schedule triggers were disabled and every workflow set to inactive. The trigger nodes were disabled rather than deleted, so they are still sitting in each workflow ready to be re-enabled and reconfigured by hand.

Two of the old workflows (Email Handling Agent and Action Items Automation) were firing every single minute. Worth deciding whether they genuinely need that cadence before switching them back on.

Outstanding Tasks

  • Re-authorise the Google OAuth credentials. Gmail, Drive, Docs, Sheets, and Chat credentials are tied to a redirect URI that pointed at the old localhost:5678 instance. Add the Cloud Run URL as an authorised redirect URI on the Google OAuth client, then reconnect each credential in the n8n UI.
  • Re-enable the triggers you actually want running, workflow by workflow.
  • Keep the old setup as a backup. The original container and D:\n8n_data were deliberately left untouched. Don't delete them until the cloud instance has proven itself over a reasonable period.

What to Expect Day to Day

  • Cold starts. The container scales to zero when idle, so the first request after a quiet period takes a few seconds to load. This is normal, not a fault.
  • Execution history is pruned after 14 days. This was switched on deliberately — the old SQLite database had grown to 1.5 GB because pruning was never configured. The historical execution logs were intentionally not migrated.
  • One instance at a time. The service is capped at a single container instance, which matches how the local setup behaved.
  • Costs. Cloud Run's free tier and Supabase's free tier cover normal usage, and there are no Cloud Scheduler jobs. The one thing to watch: CPU is set to "always allocated" (required — see the architecture notes), which means billing accrues while an instance is alive rather than only during requests. Keep an eye on the first month's usage.

Known Limitations

  • Nothing runs on a schedule right now. Until triggers are manually re-enabled, no workflow fires on its own. Workflows can still be run manually from the editor.
  • Google OAuth credentials will fail until re-authorised against the new URL.
  • Past execution history did not come across. Only workflows and credentials were migrated; the old run logs remain in the local SQLite file.
  • Supabase free-tier projects pause after 7 days of complete inactivity. Any regular workflow activity keeps it awake; if the instance sits entirely unused for over a week, the database may need waking from the Supabase dashboard.
  • Code nodes using Python may not work. The container's Python task runner isn't available; JavaScript Code nodes are unaffected.

How It Was Built (Architecture & Tech Stack)

End to end, the deployment has four moving parts:

  • Custom container image — built from the official n8nio/n8n:2.22.6 image, with five community node packages baked in at build time (Apify, ScrapingBee, SyncMate, Apollo, SerpApi). These are installed during the image build rather than at runtime, because Cloud Run's filesystem is ephemeral. The image is stored in Google Artifact Registry.
  • Cloud Run service — runs the container in australia-southeast1 (Sydney), scaling from zero to a maximum of one instance, with 1 GB memory and 1 CPU. It handles HTTPS, certificates, and routing automatically.
  • Supabase Postgres — a dedicated free-tier project in ap-southeast-2 (Sydney) that holds all n8n state. n8n connects over the session pooler with TLS verified against Supabase's certificate authority. Row-Level Security is enabled on every table, which closes off Supabase's auto-generated REST API without affecting n8n's own direct database connection.
  • Google Secret Manager — stores the three sensitive values (the n8n encryption key, the database password, and the Supabase CA certificate), injected into the container at runtime. No secrets live in the repository or in the container image.

Tech stack

  • n8n 2.22.6 (Node.js), running in Docker
  • Google Cloud Run (serverless containers) + Artifact Registry + Secret Manager
  • Supabase (managed PostgreSQL 17)
  • Configuration and docs version-controlled in GitHub

Three non-obvious configuration details were required to make this combination work, and they are worth knowing before changing anything:

  • CPU must stay "always allocated." With Cloud Run's default CPU throttling, the container's CPU is frozen between requests, which stalls n8n's background database heartbeat and makes it falsely report the database as unavailable.
  • The database CA certificate must be supplied explicitly. Supabase uses a private certificate authority that isn't in Node.js's default trust store, and n8n's option for skipping certificate verification does not work as documented — it silently falls back to an unencrypted connection that never completes.
  • The health-check endpoint had to be moved. Google Cloud Run reserves the exact path /healthz at its edge and returns its own 404 without ever passing the request to the container. n8n's editor polls that endpoint every 10 seconds to decide whether it's online, so the default configuration left the UI permanently showing "No network connection" and refusing to save. Pointing n8n at a different health path resolved it.

Operations Runbook

Redeploy after changing the image, environment variables, or secrets (not needed for workflow edits):

  • Build and push: docker build -t <artifact-registry-image> . then docker push <same>
  • Roll it out: gcloud run services update n8n --region=australia-southeast1 --image=<same>

Check service health and logs:

  • Health endpoint: curl https://n8n-659687081407.australia-southeast1.run.app/n8n-health should return {"status":"ok"}
  • Recent logs: gcloud run services logs read n8n --region=australia-southeast1 --limit=50

A note for anyone scripting this on Windows: Git Bash silently rewrites command-line values that start with / or contain :// into Windows paths, which will corrupt gcloud environment-variable values without any error. Use PowerShell for those commands, and always read the value back with gcloud run services describe to confirm it stored correctly.

Troubleshooting

  • Editor shows "Offline — No network connection" and won't save. n8n's health-check endpoint isn't reachable. Confirm N8N_ENDPOINT_HEALTH is still set to /n8n-health and that curling that path returns {"status":"ok"}. Never move it back to /healthz — Cloud Run reserves that path.
  • Blank white page. Usually means an N8N_PATH / base-path setting has been introduced. n8n does not move its REST and static assets under a base path correctly in this setup; leave the app served from the root URL.
  • "Database is not ready!" or repeated 503s. Check that the Cloud Run service still has CPU always-allocated (--no-cpu-throttling). With default throttling this appears even though the database is perfectly healthy.
  • Database connection timeouts after a config change. Verify the Supabase CA certificate is still wired into DB_POSTGRESDB_SSL_CA. Without it, the connection silently fails rather than reporting a certificate error.
  • A Google-based node suddenly fails to authenticate. Its OAuth credential likely still points at the old local redirect URI. Re-authorise it in the n8n UI against the Cloud Run URL.
  • A workflow isn't running on schedule. Expected — all triggers were disabled during migration. Open the workflow, re-enable the trigger node, and set the workflow Active.
  • Slow first load after a quiet period. Normal cold start as the container spins up from zero.
