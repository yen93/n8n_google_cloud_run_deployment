AUTOMATIONS / ROUTINES
- Scheduling approach (chosen 2026-09-14): n8n's in-process Schedule Trigger does
  NOT run on Cloud Run because min-instances=0 scales the container to zero after
  ~15 min idle and the scheduler only runs while a container is alive. Replaced by
  external HTTP calls to per-workflow Webhook Trigger URLs, driven by Supabase
  pg_cron + pg_net (fully free, in-stack). Each daily job fires an HTTP GET that
  both wakes the container and triggers the workflow.
- LIVE cron jobs (cron.job in Supabase, verified 2026-09-16): 11 active, all
  staggered every 5 min from 06:00-06:50 AM Manila, MON-FRI PHT ONLY (stored as UTC
  22:00-22:50 the prior day; pg_cron runs in UTC, no DST). Rescheduled 2026-09-16
  from the earlier ~7:00-9:30 AM spread to this tighter 6 AM block (the old 9:30 AM
  double-slot is gone), then restricted to weekdays 2026-09-16 (service fully idle
  on weekends). Day-of-week trap: schedules use dow 0-4 (Sun-Thu UTC), NOT 1-5 --
  because a 22:xx UTC run is the next morning in Manila, PHT weekday = UTC weekday
  + 1, so Mon-Fri PHT = Sun-Thu UTC. All fire an HTTP GET to a webhook, which both wakes the
  container and triggers the workflow. Live set, in run order:

- KEEP-WARM WINDOW (Cloud Scheduler, added + verified 2026-09-16): 2 jobs in
  region australia-southeast1 flip the service's min-instances via the Cloud Run
  Admin API v2 so the container is guaranteed warm around the morning batch:
    n8n-scale-up    05:50 Mon-Fri Asia/Manila -> min-instances=1  (ON)
    n8n-scale-down  07:05 Mon-Fri Asia/Manila -> min-instances=0  (OFF)
  Cloud Scheduler runs jobs in Asia/Manila directly (no DST / no PHT-8 math,
  unlike pg_cron) -- so weekday filter here is dow 1-5 (Mon-Fri PHT), whereas the
  pg_cron jobs need 0-4. Restricted to weekdays 2026-09-16 (idle on weekends). Mechanics that were non-obvious:
    * Uses a narrow field-mask PATCH (updateMask=template.scaling.minInstanceCount)
      so it changes ONLY min-instances and preserves always-allocated CPU
      (--no-cpu-throttling). Verified: after ON, minScale=1 AND cpu-throttling=false.
    * This gcloud build can't POST method PATCH from Scheduler, so the jobs POST
      with header X-HTTP-Method-Override: PATCH (googleapis.com honors it -> 200).
    * Body passed via --message-body-from-file (inline JSON mangles on Windows).
  Reverses the earlier "Cloud Scheduler deliberately avoided to keep $0" stance —
  still $0 (2 of 3 free Scheduler jobs; min=1 ~75 min/day is within Cloud Run free
  tier). Provisioning captured in cloud_run_scale_window.ps1 (repo root, idempotent,
  has a teardown block). IAM for the cloud-run-scaler SA: see ACCESS / OWNERSHIP.
- schedule_webhooks.sql (repo root) — the reference script that creates the jobs.
  Updated 2026-09-16 to match the live set: the 11 daily jobs carry the new 6 AM
  UTC schedules, and the stale intraday section (Email Handling Agent / Action
  Items) plus the unscheduled n8n-batch-mailer block were pruned to a NOT-SCHEDULED
  reference note so re-running no longer recreates dead jobs. Its 12th daily job is
  still named n8n-insta-story-scraper-log-notify-liv while the live job uses the
  friendly name "Insta Story Scraper: Log to sheet and notify Liv" — re-running
  cron.schedule() with the script name would create a SECOND job, not update the
  live one; unschedule one of the two if that happens.
- COST (Cloud Run, always-allocated 1 vCPU + 1 GiB): now that only once-daily jobs
  remain, container uptime is minimal (~daily 7-9:30 batch), so ~$0-3/month
  (mostly within the free tier). Was heading to ~$12-18/month with the intraday
  jobs. Verified via billable_instance_time metric (~10 instance-hours MTD as of
  2026-09-14).
- Webhook trigger URLs for the workflows are listed in `n8n webhooks.txt`
